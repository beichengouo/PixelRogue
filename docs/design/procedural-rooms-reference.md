# Godot 俯视角 Roguelike：程序化房间生成系统设计方案

> 目标：为一个"一个房间一屏、房间之间通过门连接"的俯视角动作
> Roguelike，设计一套可复现、可验证、可扩展的程序化楼层生成系统。\
> 设计参考：《以撒的结合》的地图拓扑、分支探索、特殊房间规则与房间模板思路。本文是独立的架构方案，并非《以撒的结合》原始实现或源码。

## 1. 设计目标与原则

系统应优先保证：

1.  **可通关**：起始房间与 Boss 房之间始终存在有效路径。
2.  **值得探索**：地图包含分支、死路、可选奖励和风险收益选择。
3.  **可控**：可以通过配置调整地图规模、分支密度、循环路径和特殊房间分布。
4.  **可复现**：相同种子和相同生成器版本应得到相同地图，便于调试与测试。
5.  **易扩展**：后续可加入隐藏房、钥匙门、多格房间、传送门、挑战房等机制。
6.  **职责分离**：地图数据生成与 Godot
    场景实例化分开，避免生成算法和游戏节点相互耦合。

### 第一版建议范围

先实现： - 单格房间； - 上、下、左、右四向连接； - 起始房、普通房、Boss
房、宝箱房、商店； - 树状骨架 + 少量循环连接； -
连通性与特殊房间验证； - 小地图显示。

暂时不做： - 多格房间； - 隐藏房和爆破墙； - 单向门、钥匙门； -
复杂地形模板自动匹配。

先确保地图结构稳定，再逐步扩展。

## 2. 总体架构

建议拆分为以下模块：

  -----------------------------------------------------------------------------------------------
  模块                    建议文件                 职责
  ----------------------- ------------------------ ----------------------------------------------
  生成配置                `FloorConfig.gd`         种子、目标房间数、边界、分支和循环参数

  地图生成器              `FloorGenerator.gd`      生成坐标、房间与连接关系

  地图验证器              `FloorValidator.gd`      检查连通性、死路、路径长度、门连接与特殊房间

  特殊房分配器            `SpecialRoomPlacer.gd`   分配 Boss、宝箱、商店等类型

  房间数据                `RoomData.gd`            保存单个房间的逻辑数据

  场景构建器              `DungeonBuilder.gd`      将逻辑数据实例化为实际房间场景

  房间场景                `Room.tscn`              单屏房间的基础结构

  门控制器                `DoorController.gd`      开关门、锁门、切换房间

  小地图                  `Minimap.gd`             显示已探索房间、特殊房间和连接关系
  -----------------------------------------------------------------------------------------------

推荐流程：

``` text
FloorConfig
    ↓
FloorGenerator：生成地图骨架
    ↓
FloorValidator：验证结构
    ↓
SpecialRoomPlacer：分配特殊房间
    ↓
FloorValidator：验证特殊房间规则
    ↓
DungeonBuilder：实例化房间与门
    ↓
游戏运行：探索、战斗、保存进度
```

**核心原则：生成器只生成数据，构建器才创建节点。**
这样更换生成算法时，不必重写房间场景和门逻辑。

## 3. 数据结构：网格位置与连接关系分离

### 3.1 房间数据

每个房间保存自己的网格坐标、类型、邻接连接和运行状态。

``` gdscript
# RoomData.gd
class_name RoomData
extends RefCounted

var grid_pos: Vector2i
var room_type: String = "normal"

# 只记录实际存在的门连接
var links: Array[Vector2i] = []

var visited: bool = false
var cleared: bool = false
var template_id: String = ""
var difficulty: int = 1
```

### 3.2 楼层数据

``` gdscript
# 楼层数据的核心字段，可放在 FloorGenerator 或独立 FloorData 中
var rooms: Dictionary = {} # Vector2i -> RoomData

var start_pos: Vector2i
var boss_pos: Vector2i
var seed_value: int
```

使用 `Vector2i` 作为字典键，可以直接查询指定网格位置是否有房间。

### 3.3 为什么位置与连接必须分开？

-   **网格坐标**负责空间布局：边界、占位、相邻关系。
-   **连接图**负责探索逻辑：门、路线、分支、死路和可达性。

例如，A 房在 `(0, 0)`，B 房在 `(1, 0)`。两者虽然坐标相邻，但只有在双方
`links` 中都记录对方时，才表示有一扇可以通行的门。

这种设计为未来加入钥匙门、隐藏门、单向门和传送门留下了空间。

## 4. 生成算法：树状骨架 + 循环路径

第一版建议采用**带权随机前沿扩展算法**。它实现简单、可控，适合单屏房间组成的网格地图。

不建议一开始使用复杂的 Wave Function
Collapse（WFC）。当前最重要的是地图拓扑和分支探索，而不是墙壁、地板等局部图案匹配。

### 阶段 A：从起始房向外扩展

1.  在 `(0, 0)` 创建起始房。
2.  收集所有现有房间周围的空网格位置，形成候选集合。
3.  排除越界位置，以及不符合空间规则的位置。
4.  按权重从候选位置中抽取一个位置。
5.  从该位置相邻的已有房间中，选择一个作为父房间。
6.  创建新房间，并只与父房间建立连接。
7.  重复直到达到目标房间数量，或候选集合为空。

新房间首次放置时只建立一条父子连接。不要因为两个房间坐标相邻，就自动开门。这样可以先控制树状结构，再有选择地添加循环路径。

### 阶段 B：通过权重控制地图形状

以下是可用于原型测试的初始参数，并非唯一正确的数值：

    候选位置周围已有房间数   建议权重 目的
  ------------------------ ---------- ------------------------
                         1       1.00 优先扩展，保持空间充足
                         2       0.45 允许局部变紧凑
                         3       0.15 减少拥挤位置扩展
                         4       0.03 极少使用，避免局部填满

加权随机抽取概率为：

\\\[ P(i)=\\frac{w_i}{\\sum_j w_j} \\\]

权重越高，候选位置越容易被选中。地图过于狭长时，可以适当增加周围已有两个房间的候选权重；地图过于拥挤时，则降低周围已有三个或四个房间的候选权重。

### 阶段 C：增加少量循环路径

如果所有房间只连接父子节点，最终地图是一棵树。它保证连通，但可能过于线性，玩家走进分支后通常只能原路返回。

因此，在生成树状骨架后，扫描所有**坐标相邻但尚未连接**的房间对，随机选取少量连接作为循环路径。

初始建议： - 每层增加 1--3 条循环连接； - 不得产生重复连接； -
只连接已经存在且坐标相邻的房间； -
优先连接不同分支，或能明显缩短回程的房间； -
地图较小或已经紧凑时，减少循环数量。

循环连接不应完全随机。可计算添加某条边前后的最短路径变化，优先考虑能减少长距离回程、同时不会破坏关键路线节奏的连接。

## 5. 地图生成约束

生成器必须明确检查规则，而不是只依赖随机概率。

### 5.1 硬性约束

以下条件必须满足，否则重新生成或修复地图：

-   起始房存在且只有一个；
-   Boss 房存在且只有一个；
-   所有房间都能从起始房到达；
-   房间坐标不重复；
-   每条连接都指向一个实际存在的房间；
-   连接必须是上下左右相邻的房间；
-   A 连接 B 时，B 必须同时连接 A；
-   特殊房间不能被分配到同一房间；
-   Boss 房与起始房不能重合；
-   房间数量在配置允许的范围内。

### 5.2 软性约束

这些条件不一定导致生成失败，但应计分或调节权重：

-   死路数量是否合适；
-   起点到 Boss 的路径是否过短或过长；
-   分支是否过于集中；
-   商店、宝箱等奖励是否过于接近起点；
-   是否存在大量长度为 1 的无意义分支；
-   地图形状是否过于狭长或过于紧凑；
-   循环路径是否太多，以至于分支探索失去意义。

### 5.3 推荐的原型参数

  参数                     建议起始值 说明
  ---------------------- ------------ ----------------------
  目标房间数                   12--18 普通楼层原型规模
  地图边界                  `[-6, 6]` x、y 轴的坐标范围
  循环连接数                     1--3 控制捷径和回路
  最少死路                          3 提供分支探索机会
  起点到 Boss 最短距离              4 避免 Boss 离起点太近
  生成重试次数                     30 达不到约束时重试
  每个房间初始连接数                1 先构建树状骨架

这些参数应当在游戏测试后调整。不同游戏节奏、房间规模和战斗时长会影响最合适的数值。

## 6. 特殊房间分配策略

建议先生成普通地图结构，再把普通房间转换成特殊房间类型。这样更容易保证拓扑稳定。

### 6.1 推荐放置顺序

1.  起始房：在地图创建时固定。
2.  Boss 房：从远离起点、且满足路径长度要求的死路中选择。
3.  宝箱房：优先从其他死路中选择，保持探索价值。
4.  商店：根据楼层规则，从可达且不与关键房间冲突的位置中选择。
5.  挑战房、诅咒房等：按难度和风险收益规则分配。
6.  隐藏房：后续版本再加入，不纳入第一版基础连通图。

### 6.2 Boss 房的选择

可计算从起始房到每个候选房间的最短路径长度，然后筛选：

-   房间不是起始房；
-   房间是死路或符合指定的终点条件；
-   与起点距离不小于阈值；
-   房间周围存在可放置门的位置；
-   不与其他已分配特殊房间冲突。

在合格候选中，优先选择距离较远的房间，再从前几名中加权随机选择。这样既能控制关卡节奏，也不会每次都生成完全相同的
Boss 方向。

### 6.3 死路不是越多越好

死路最好承载明确的玩法意义：

-   奖励型：宝箱、强化、资源；
-   风险型：精英敌人、陷阱、挑战；
-   选择型：商店、祭坛、消耗资源换奖励；
-   信息型：地图线索、剧情或特殊事件。

让玩家知道偏离主路线可能得到什么，探索决策才有意义。

## 7. Godot 实现骨架

以下代码用于说明核心结构。正式项目中应拆分成独立脚本，并补齐错误处理和验证。

### 7.1 带权随机抽取

``` gdscript
func weighted_pick_index(weights: Array[float], rng: RandomNumberGenerator) -> int:
    var total := 0.0
    for weight in weights:
        total += maxf(weight, 0.0)

    if total <= 0.0:
        return -1

    var roll := rng.randf() * total
    for i in range(weights.size()):
        roll -= maxf(weights[i], 0.0)
        if roll <= 0.0:
            return i

    return weights.size() - 1
```

### 7.2 四方向邻居

``` gdscript
const DIRECTIONS: Array[Vector2i] = [
    Vector2i.UP,
    Vector2i.DOWN,
    Vector2i.LEFT,
    Vector2i.RIGHT
]
```

### 7.3 判断候选位置周围已有多少房间

``` gdscript
func count_occupied_neighbors(pos: Vector2i, rooms: Dictionary) -> int:
    var count := 0
    for direction in DIRECTIONS:
        if rooms.has(pos + direction):
            count += 1
    return count
```

### 7.4 建立双向连接

``` gdscript
func connect_rooms(a: RoomData, b: RoomData) -> void:
    if not a.links.has(b.grid_pos):
        a.links.append(b.grid_pos)
    if not b.links.has(a.grid_pos):
        b.links.append(a.grid_pos)
```

**注意：**
连接函数应当保证双向一致。不要只给一侧添加邻接记录，否则小地图、门生成和路径搜索可能出现不一致。

## 8. 连通性与路径验证

建议用 BFS（广度优先搜索）检查地图连通性和最短路径。

### 8.1 BFS 伪代码

``` text
queue = [start]
visited = {start}
distance[start] = 0

while queue is not empty:
    current = queue.pop_front()

    for next in current.links:
        if next not in visited:
            visited.add(next)
            distance[next] = distance[current] + 1
            queue.push_back(next)

地图连通，当且仅当 visited 数量等于房间总数。
distance[boss] 即起点到 Boss 的最短门数。
```

验证器至少应检查： - 是否所有房间都被 BFS 访问； - Boss 是否可达； -
每条连接是否双向； - 每个连接的坐标差是否为上下左右单位距离； -
特殊房间是否重复分配； - 死路数量是否达到最低要求。

### 8.2 失败处理

推荐使用"有限重试 + 安全回退"：

1.  尝试生成地图；
2.  验证硬性约束；
3.  如果失败，重新生成；
4.  达到最大重试次数后，生成一张已知有效的简单地图，或调用确定性修复逻辑；
5.  在开发模式记录失败原因、种子和尝试次数。

不要无限重试，否则在约束过严时可能卡住游戏。

## 9. Godot 场景构建与门系统

逻辑地图生成完成后，才创建场景。

### 9.1 单房间场景建议

``` text
Room.tscn
└── Room (Node2D)
    ├── TileMapLayer / TileMap
    ├── Props (Node2D)
    ├── Enemies (Node2D)
    ├── Pickups (Node2D)
    ├── Doors (Node2D)
    │   ├── NorthDoor
    │   ├── SouthDoor
    │   ├── WestDoor
    │   └── EastDoor
    └── RoomCamera (Camera2D)
```

根据实际项目使用的 Godot 4 小版本，瓦片节点可以是 `TileMapLayer`
或项目当前采用的 TileMap 结构。

### 9.2 房间世界坐标

如果每个房间尺寸为 `room_pixel_size`，则：

``` gdscript
func grid_to_world(grid_pos: Vector2i, room_pixel_size: Vector2) -> Vector2:
    return Vector2(
        grid_pos.x * room_pixel_size.x,
        grid_pos.y * room_pixel_size.y
    )
```

### 9.3 门的生成规则

对于房间 `room`，只根据它的 `links` 创建门：

-   存在 `room.grid_pos + Vector2i.UP` 的连接：创建北门；
-   存在下方连接：创建南门；
-   存在左方连接：创建西门；
-   存在右方连接：创建东门。

门的朝向、碰撞体、动画和目标房间坐标应当由 `DoorController.gd` 管理。

房间切换时建议： 1. 记录玩家从哪一侧进入； 2.
将玩家放置在目标房间对应门的内侧； 3. 更新当前房间； 4. 更新小地图； 5.
根据规则决定门是否关闭、战斗是否开始。

## 10. 房间模板库设计

地图拓扑决定"去哪儿"，模板决定"房间里面长什么样"。

第一版可以手工制作 20--40 个单屏房间模板，每个模板附带元数据：

  字段               示例                用途
  ------------------ ------------------- --------------
  `template_id`      `combat_cross_01`   唯一标识
  `room_type`        `normal`            房间类别
  `difficulty`       `2`                 难度等级
  `required_doors`   `N, E`              必须支持的门
  `weight`           `1.0`               被选中权重
  `chapter_tags`     `cave`              适用章节
  `has_pits`         `true`              地形标签
  `enemy_budget`     `5`                 敌人强度预算

模板选择时，先筛选满足门方向、房间类型和章节条件的模板，再按权重随机选择。不要在模板不支持某方向门时强行放置门。

## 11. 随机种子与调试工具

### 11.1 可复现生成

使用 `RandomNumberGenerator`：

``` gdscript
var rng := RandomNumberGenerator.new()
rng.seed = seed_value
```

测试时固定 `seed_value`；正式游戏可以在每层开始时生成或读取种子。

如果地图拓扑、模板选择和敌人生成共用同一个随机数流，改动敌人生成逻辑就可能改变后续地图结果。更稳定的做法是为各阶段派生独立种子，例如： -
`topology_seed` - `template_seed` - `content_seed`

也可以为每个阶段创建独立的随机数生成器。

### 11.2 开发模式可视化

建议实现一个简单的调试地图： - 每个房间绘制一个方块； -
门连接绘制成线； - 不同房间类型使用不同颜色或标签； - 显示坐标、房间
ID、模板 ID； - 高亮起始房到 Boss 的最短路径； -
标出死路、循环边和不可达房间。

增加批量测试按钮，一次生成 100--1000 张地图，输出： - 生成成功率； -
平均重试次数； - 平均房间数； - 起点到 Boss 的平均距离； -
平均死路数； - 平均循环数； - 无效地图的种子和失败原因。

这比只凭肉眼试玩更容易发现生成器的结构性问题。

## 12. 分阶段实施计划

### 阶段 1：最小可用地图生成器

目标：能生成一张逻辑正确的房间图。

任务： - 建立 `RoomData.gd`； - 建立 `FloorGenerator.gd`； -
实现网格占位和四方向扩展； - 生成固定数量的房间； - 实现双向连接； -
实现 BFS 连通性验证； - 在调试界面绘制房间图。

验收标准： - 能生成目标数量附近的房间； - 所有房间都能从起点到达； -
不存在重复坐标； - 同一种子能复现同一张拓扑地图。

### 阶段 2：分支与探索节奏

任务： - 调整候选位置权重； - 计算死路数量； - 添加循环连接； -
计算起点到各房间的最短路径； - 设置 Boss 最小路径距离； -
增加地图形状统计。

验收标准： - 地图不是单纯的长走廊； - 存在有意义的分支和死路； -
不会出现大量无意义的短枝； - Boss 房不会离起点过近。

### 阶段 3：特殊房间

任务： - 放置 Boss 房； - 放置宝箱房和商店； -
为不同楼层配置特殊房间规则； - 检查特殊房间唯一性与可达性。

验收标准： - 必须出现的特殊房间均能放置； - 可选特殊房间不违反规则； -
特殊房间不会挤占起始房或 Boss 房。

### 阶段 4：实际游戏场景

任务： - 制作 `Room.tscn`； - 根据连接图实例化房间； -
根据连接方向生成门； - 实现门触发、玩家传送和相机切换； - 接入小地图。

验收标准： - 门两侧一致； - 玩家不会被传送到墙内； -
小地图与实际可通行连接一致； - 所有生成的房间都能正常进入和离开。

### 阶段 5：模板与内容生成

任务： - 制作房间模板库； - 根据房间类型和门方向筛选模板； -
按难度预算生成敌人； - 为奖励、陷阱和道具添加约束。

验收标准： - 模板与门连接匹配； - 同类房间具有足够变化； -
难度随着楼层推进而合理增长； -
不会出现奖励无法到达或敌人堵死出口的情况。

### 阶段 6：自动化测试与扩展

任务： - 批量生成数百张地图； - 统计结构指标； - 保存失败种子； -
加入隐藏房、钥匙门、多格房间等高级机制。

验收标准： - 批量生成时没有不可恢复的失败； - 失败可通过种子稳定复现； -
新机制加入后，原有验证规则仍然有效。

## 13. 常见错误与规避方式

**错误一：坐标相邻就自动连门。**\
这会导致生成器失去对路线的控制。应当以显式 `links` 为准。

**错误二：在生成地图时立即实例化场景。**\
算法失败后会产生大量节点清理问题。先生成纯数据，通过验证后再构建场景。

**错误三：只检查房间数量，不检查连通性。**\
房间数够了不代表地图可玩。必须进行 BFS 验证。

**错误四：所有特殊房间完全随机。**\
可能导致 Boss
过近、奖励集中或关卡节奏失衡。使用位置、距离和唯一性规则筛选候选。

**错误五：重试没有上限。**\
严格约束可能让算法无限尝试。使用最大重试次数，并准备回退地图。

**错误六：把所有随机逻辑绑定在同一个随机数流上。**\
增加一个敌人抽取步骤就可能改变后续地图。为拓扑、模板和内容使用独立随机流。

## 14. 推荐的第一版目标

建议第一版明确控制范围：

-   12--18 个房间；
-   单格房间；
-   四向门；
-   1 个起始房；
-   1 个 Boss 房；
-   1 个宝箱房；
-   可选商店；
-   3 个或更多死路；
-   1--3 条循环连接；
-   BFS 连通性验证；
-   固定种子复现；
-   可视化调试地图；
-   20--40 个房间模板作为后续目标。

先完成这套最小系统，之后再依据实际试玩数据调整分支密度、地图规模和特殊房间规则。

## 15. 最终建议

最值得借鉴《以撒的结合》的不是某一个具体随机算法，而是它的设计分层：

1.  **地图拓扑**决定探索路线；
2.  **特殊房间规则**控制关卡节奏；
3.  **房间模板**保证战斗空间的可玩性；
4.  **随机内容**制造重复游玩的变化；
5.  **验证与种子系统**保证生成质量和可调试性。

对你的 Godot 项目来说，优先实现"树状地图骨架 + 少量循环 + BFS 验证 +
特殊房间分配"，是投入产出比最高的起点。
